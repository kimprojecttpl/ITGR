## 1. Problem Statement

ทุกวันนี้ข้อมูลสถานะ ITGR ทั้ง 96 ข้ออยู่ใน Supabase และเข้าถึงได้ทางเดียวคือ**เปิดเว็บแล้วล็อกอินด้วย PIN** เพราะ session เป็น JWT ใน httpOnly cookie ที่ตั้ง `sameSite: strict` ([lib/auth.js:37](../lib/auth.js)) — ระบบภายนอกเรียกไม่ได้เลยแม้แต่ทางเดียว

ผลคือคำถามที่ตอบได้ใน 3 วินาทีถ้ามี API เช่น *"หมวดไหนยังแดงอยู่บ้าง"* / *"มีกี่ข้อที่รอผมอนุมัติ"* / *"ข้อที่ Very High risk ยังไม่เริ่มมีอะไรบ้าง"* ต้องเปิดเว็บ กรองเอง อ่านเอง ทุกครั้ง และเอาเข้า Morning Brief หรือ workflow อัตโนมัติไม่ได้

**ต้นทุนของการไม่แก้:** ข้อมูล compliance ที่อัปเดตอยู่ตลอดถูกขังอยู่ในเว็บเดียว ใช้ประกอบการตัดสินใจประจำวันไม่ได้ และเมื่อใกล้กำหนดส่ง Marubeni การรวบสถานะยังต้องทำด้วยมือ

## 2. Goals

| # | เป้าหมาย | วัดยังไง |
|---|---|---|
| G1 | ระบบ AI ภายนอกถามสถานะงานได้โดยไม่ต้องมีคนเปิดเว็บ | ≥ 90% ของคำถามที่ตั้งไว้ในชุดทดสอบ ตอบได้จบใน ≤ 2 API call |
| G2 | ต่อของใหม่เข้าได้ในเวลาไม่กี่นาที ไม่ต้องอ่านโค้ด | ออก token + ยิงคำถามแรกสำเร็จภายใน **10 นาที** โดยใช้แค่เอกสารที่ API ให้เอง |
| G3 | เปิดช่องทางใหม่โดยไม่ลดความปลอดภัยของระบบเดิม | token รั่ว 1 ใบ = เพิกถอนได้ทันที และ**เขียนข้อมูลไม่ได้เลยแม้แต่ field เดียว** |
| G4 | ทุกการเรียกจากภายนอกตรวจสอบย้อนหลังได้ | 100% ของ request มี log ว่า token ไหน ถามอะไร เมื่อไหร่ |

## 3. Non-Goals

| ไม่ทำ | เพราะอะไร |
|---|---|
| **เขียน/แก้ข้อมูลผ่าน API** | v1 ตัดความเสี่ยงทิ้งทั้งก้อน เอกสารนี้เป็นหลักฐาน audit — ถ้าให้เขียนได้ต้องออกแบบว่า "AI แก้ในนามใคร" ซึ่งกระทบหลักการแบ่งแยกหน้าที่ User→Reviewer→Approver ทั้งชุด |
| **เดิน workflow (submit / review / approve)** | เหตุผลเดียวกัน และหนักกว่า — การอนุมัติต้องผูกกับตัวบุคคลจริงเสมอ |
| **ดึงไฟล์หลักฐาน (evidence files)** | ไฟล์อยู่ใน private bucket และแจก signed URL อยู่แล้ว การส่งออกทาง API เท่ากับเปิดช่องรั่วของเอกสารลับ |
| **แปลภาษาคนเป็น query ฝั่งเซิร์ฟเวอร์** | ตกลงแล้วว่าให้ฝั่งผู้เรียกทำ — ประหยัดกว่า เร็วกว่า และ ITGR ไม่ต้องถือ API key ของ LLM เจ้าไหนเลย |
| **Outbound webhook (ยิงแจ้งเตือนออกเมื่อสถานะเปลี่ยน)** | เป็นคนละทิศกับที่ขอ (ขาเข้า vs ขาออก) และต้องมี retry/dedup/secret rotation เป็นของตัวเอง — ดู P2 |
| **เปิดให้บุคคลภายนอก/Marubeni เรียกโดยตรง** | v1 จำกัดที่เครื่องมือของต้น ถ้าเปิดให้ภายนอกต้องเพิ่ม scope ต่อ token, หมดอายุบังคับ, และข้อตกลงการใช้ข้อมูล |

## 4. User Stories

**ในฐานะเจ้าของระบบ (ต้น)**
- อยากออก API token ตั้งชื่อได้ว่าใบไหนของเครื่องมืออะไร เพื่อจะได้เพิกถอนเฉพาะใบที่รั่วโดยไม่กระทบตัวอื่น
- อยากเห็นว่า token ใบไหนถูกใช้ล่าสุดเมื่อไหร่ เพื่อจะได้ลบใบที่ไม่ได้ใช้แล้วทิ้ง
- อยากให้ token ที่เพิกถอนแล้วใช้ไม่ได้ทันที ไม่ต้องรอ deploy

**ในฐานะ AI ที่เรียกใช้ (n8n / LINE bot / Claude)**
- อยากอ่านคำอธิบายโครงสร้างข้อมูลจาก endpoint เดียว เพื่อจะได้รู้เองว่ามีสถานะอะไรบ้าง หมวดอะไรบ้าง กรองด้วยอะไรได้ โดยไม่ต้องให้คนมาบอก
- อยากกรองรายการด้วยหมวด/ความเสี่ยง/สถานะ/ผู้รับผิดชอบ แล้วได้ผลเป็น JSON ที่สรุปต่อได้ทันที
- อยากขอ**ตัวเลขสรุป**ทีเดียว (ความคืบหน้ารวม เกรด รายหมวด) โดยไม่ต้องดึง 96 ข้อมานับเอง
- อยากเลือกภาษาไทยหรืออังกฤษได้ เพื่อจะได้ตอบผู้ใช้เป็นภาษาที่เขาถามมา
- เมื่อ token ผิดหรือหมดอายุ อยากได้ error ที่บอกสาเหตุชัด ๆ เพื่อจะได้ไม่ retry วนไปเรื่อย

**กรณีขอบ**
- เมื่อถามข้อที่ไม่มีอยู่ (เช่น ข้อ 200) ต้องได้ 404 พร้อมข้อความที่เข้าใจได้ ไม่ใช่ 500
- เมื่อยิงถี่เกินกำหนด ต้องได้ 429 พร้อมบอกว่ารออีกกี่วินาที
- เมื่อกรองแล้วไม่เจออะไรเลย ต้องได้ `200` กับ list ว่าง ไม่ใช่ error

## 5. Requirements

### P0 — ไม่มีไม่ได้

**R1. ตาราง `api_tokens` + การออก/เพิกถอน token**

```sql
create table if not exists api_tokens (
  id          uuid primary key default gen_random_uuid(),
  name        text not null,              -- "n8n morning brief", "LINE bot"
  token_hash  text not null unique,       -- HMAC-SHA256(token, API_TOKEN_PEPPER)
  prefix      text not null,              -- 12 ตัวแรก ไว้โชว์ในหน้า admin
  scopes      text[] not null default '{items:read,summary:read}',
                                          -- scope ที่มี: items:read · summary:read · history:read
  active      boolean not null default true,
  expires_at  timestamptz,                -- ค่าเริ่มต้น null = ไม่หมดอายุ (D2) — คงคอลัมน์ไว้
                                          -- เผื่อวันหนึ่งต้องออก token ชั่วคราว
  last_used_at timestamptz,
  created_by  uuid references users (id) on delete set null,
  created_at  timestamptz not null default now()
);
```

ใช้แนวเดียวกับ [lib/pin.js](../lib/pin.js) เป๊ะ — keyed hash + unique index เพื่อ lookup O(1) โดยที่ DB dump อย่างเดียวถอด token ไม่ได้ **ใช้ pepper คนละตัวกับ PIN** (`API_TOKEN_PEPPER`) เพื่อไม่ให้การหมุน secret ของ API ไปทำ PIN ของทุกคนพัง

รูปแบบ token: `itgr_live_<32 bytes base62>` — โชว์ค่าเต็ม**ครั้งเดียวตอนสร้าง** หลังจากนั้นดูได้แค่ prefix

*Acceptance:*
- [ ] admin สร้าง token ได้จากแท็บ Admin ตั้งชื่อ + เลือก scope ได้
- [ ] **ค่าเริ่มต้นคือไม่หมดอายุ** (D2) แต่กรอกวันหมดอายุเองได้ถ้าต้องการ token ชั่วคราว
- [ ] ค่าเต็มโชว์ครั้งเดียว ปิดแล้วดูซ้ำไม่ได้
- [ ] กด revoke แล้ว request ถัดไปได้ 401 ทันที ไม่ต้อง deploy
- [ ] token ที่กรอก `expires_at` ไว้และผ่านแล้ว ได้ 401 พร้อม `code: "token_expired"`
- [ ] ค่า token เต็มไม่เคยปรากฏใน log, error message หรือ response ใด ๆ
- [ ] หน้า Admin แสดง `last_used_at` ของทุกใบ และ**เน้นสีใบที่ไม่ถูกใช้เกิน 90 วัน** — เมื่อ token ไม่หมดอายุเอง สิ่งนี้คือกลไกเดียวที่จะทำให้เห็นใบที่ลืมทิ้งไว้

**R2. Bearer auth middleware แยกจาก session เดิม**

`Authorization: Bearer itgr_live_...` — คนละทางกับ cookie โดยสิ้นเชิง โค้ด session เดิมไม่ต้องแตะ

*Acceptance:*
- [ ] ไม่มี header → 401 `missing_token`
- [ ] token ผิด/ถูกเพิกถอน/หมดอายุ → 401 พร้อม `code` แยกกรณี
- [ ] token ที่ไม่มี scope ที่ endpoint ต้องการ → 403 `insufficient_scope`
- [ ] cookie session **ใช้กับ `/api/v1/*` ไม่ได้** และ bearer token **ใช้กับ endpoint เดิมไม่ได้** (แยกขาดสองทาง)
- [ ] ไม่ส่ง CORS header ใด ๆ เลย — เรียกจาก JavaScript ในเบราว์เซอร์ไม่ได้ (กันคนเอา token ไปฝังหน้าเว็บ)
- [ ] อัปเดต `last_used_at` แบบไม่บล็อก response

**R3. `GET /api/v1/meta` — เอกสารที่เครื่องอ่านเองได้ (หัวใจของฟีเจอร์นี้)**

นี่คือสิ่งที่ทำให้ "ถามแบบ Vibe" ทำงานได้จริงทั้งที่ ITGR ไม่มี LLM: AI ฝั่งโน้นดึง endpoint นี้ครั้งเดียวแล้วรู้ทุกอย่างที่ต้องรู้เพื่อประกอบ query เอง

ต้องคืน: รายชื่อหมวดทั้ง 8 (ไทย+อังกฤษ), ค่า `status` ที่เป็นไปได้ทั้ง 5, `workflow_state` ทั้ง 8, ระดับความเสี่ยง 4 ระดับ, ลำดับความสำคัญ, เกณฑ์เกรด A–E, พารามิเตอร์ที่กรองได้ทั้งหมดพร้อมชนิดข้อมูล, และ**ตัวอย่างคำถามภาษาคน 5–10 อันคู่กับ URL ที่ควรยิง**

*Acceptance:*
- [ ] ค่า enum ทั้งหมดอ่านจากที่เดียวกับที่ UI ใช้ ไม่ได้ hardcode ซ้ำ (ถ้าเพิ่มสถานะใหม่แล้วลืมแก้ที่นี่ = ถือว่าไม่ผ่าน)
- [ ] มี `example_questions` เป็นคู่ `{ question_th, question_en, request }`
- [ ] ตอบได้โดยไม่ต้องแตะตาราง items (cache ได้ 1 ชม.)

**R4. `GET /api/v1/items` — ค้นและกรอง**

พารามิเตอร์: `cat`, `risk`, `priority`, `status`, `workflow_state`, `owner`, `article`, `q` (ค้นข้อความ ครอบคลุมทั้งไทยและอังกฤษเสมอ ไม่ว่าจะขอ `lang` อะไร), `updated_since`, `lang=th|en` (ค่าเริ่มต้น `th`), `fields`, `limit` (ค่าเริ่มต้น 25 / สูงสุด 100), `offset`

*Acceptance:*
- [ ] กรองหลายตัวพร้อมกันได้ ตีความแบบ AND
- [ ] `lang=th` คืน `name`/`content`/`standard`/`evidence` เป็นไทย และ fallback เป็นอังกฤษเมื่อยังไม่มีคำแปล (ตรรกะเดียวกับ UI)
- [ ] ตอบกลับมี `total` + `has_more` เสมอ เพื่อให้ AI รู้ว่ายังมีต่อ
- [ ] ค่ากรองที่ไม่ถูกต้อง (เช่น `status=Banana`) → 400 พร้อม**บอกค่าที่ถูกต้อง** ในข้อความ error
- [ ] ไม่คืนข้อมูลหลักฐานไฟล์และไม่คืน `users.pin_hash` หรือฟิลด์ผู้ใช้ใด ๆ
- [ ] `limit` เกิน 100 → บีบลงเหลือ 100 (ไม่ error) และตอบว่าบีบแล้ว

**R5. `GET /api/v1/summary` — ตัวเลขสรุปในหนึ่งครั้ง**

ความคืบหน้ารวม %, เกรดรวม, รายหมวด (%, เกรด, จำนวนข้อ), นับตามสถานะ, นับตามความเสี่ยง, จำนวนที่ค้างในแต่ละขั้น workflow, และจำนวนข้อ Very High risk ที่ยังไม่เริ่ม

*Acceptance:*
- [ ] ตัวเลข % และเกรด**ตรงกับที่หน้า Overview แสดง** ทุกตัว (คำนวณด้วยตรรกะเดียวกัน ไม่เขียนใหม่)
- [ ] รับ `cat` เพื่อดูเฉพาะหมวดได้
- [ ] ตอบใน 1 request ไม่ต้องให้ผู้เรียกดึง 96 ข้อมานับเอง

**R6. `GET /api/v1/items/{no}` และ `GET /api/v1/items/{no}/history`**

รายละเอียดข้อเดียว + ไทม์ไลน์ workflow (ใคร เปลี่ยนสถานะอะไร เมื่อไหร่ ความเห็นอะไร) — **ชื่อไฟล์หลักฐานแสดงได้ แต่ไม่มีลิงก์และไม่มีตัวไฟล์**

**history อยู่หลัง scope ของตัวเอง (`history:read`)** ตามที่ตกลงใน D3 — ความเห็นตอนตีกลับมักมีเนื้อหาตรงไปตรงมาเรื่องคนและงาน จึงไม่ควรติดมากับ token ที่ออกไว้แค่ให้ดูสถานะรวม

*Acceptance:*
- [ ] `GET /items/{no}` ใช้ scope `items:read` ตามปกติ
- [ ] `GET /items/{no}/history` **ต้องมี `history:read`** ไม่มี → 403 `insufficient_scope`
- [ ] `history:read` ไม่อยู่ใน scope เริ่มต้น ต้องติ๊กเลือกเองตอนสร้าง token
- [ ] `GET /items/{no}` ที่ไม่มี `history:read` ต้องไม่มีฟิลด์ความเห็นหรือไทม์ไลน์ติดมาในช่องทางอ้อม
- [ ] ข้อที่ไม่มีอยู่ → 404 `item_not_found` ไม่ใช่ 500
- [ ] history เรียงเก่า→ใหม่ และมีชื่อผู้ทำรายการ
- [ ] ไม่มี signed URL ของไฟล์ใด ๆ ใน response

**R7. Rate limit + บันทึกการเรียก**

*Acceptance:*
- [ ] จำกัดต่อ token (ค่าตั้งต้นเสนอ 60 req/นาที) เกินแล้วได้ 429 + `Retry-After`
- [ ] ทุก request บันทึก: token id, path, พารามิเตอร์ที่ใช้, HTTP status, เวลาที่ใช้ — **ไม่บันทึกค่า token**
- [ ] admin ดูประวัติการเรียกล่าสุดได้จากแท็บ Admin

**R8. รูปแบบ error ที่เครื่องเข้าใจตรงกันทุก endpoint**

```json
{ "error": { "code": "invalid_filter", "message": "...", "allowed_values": ["Not Started","In Progress","Compliant","Partial","Not Compliant"] } }
```

*Acceptance:*
- [ ] ทุก error มี `code` แบบ machine-readable
- [ ] error ที่แก้ได้ด้วยการยิงใหม่ให้ข้อมูลพอที่จะแก้เองได้ (เช่น รายการค่าที่ถูกต้อง)

### P1 — อยากได้ ตามหลังได้

- **`GET /api/v1/openapi.json`** — OpenAPI 3.1 ให้ n8n / Custom GPT / Claude นำเข้าเป็น tool อัตโนมัติ ไม่ต้องเขียน integration ด้วยมือ *(อันนี้คือตัวที่ทำให้ G2 เหลือ 10 นาทีจริง ๆ ถ้าทำได้ทันควรดันขึ้น P0)*
- **`GET /api/v1/appendices`** — ภาคผนวก 1–5 สองภาษา สำหรับตอบคำถามอ้างอิงข้อกำหนด
- **IP allowlist ต่อ token** — ล็อกให้เรียกได้จาก IP ของ n8n เท่านั้น *(น้ำหนักมากขึ้นหลัง D2: เมื่อ token ไม่หมดอายุ นี่คือด่านที่สองที่ทำให้ token ที่หลุดออกไปใช้จากที่อื่นไม่ได้ — ควรพิจารณาดันขึ้น P0 พร้อม `openapi.json`)*
- **`X-Request-Id`** ในทุก response เพื่อไล่ปัญหาข้ามระบบ
- **`updated_since` แบบ delta** สำหรับ Morning Brief ("มีอะไรเปลี่ยนตั้งแต่เมื่อวาน")

### P2 — เผื่อไว้ในสถาปัตยกรรม ยังไม่สร้าง

- **Outbound webhook** เมื่อสถานะเปลี่ยน (ยิงเข้า n8n/LINE) — ออกแบบ `api_tokens.scopes` เผื่อรองรับ `events:subscribe` ไว้แล้ว
- **MCP server** ห่อ API นี้ ให้ Claude ต่อตรงเป็น tool
- **Write scope** (`items:write`) สำหรับอัปเดต owner/note/ClickUp — ต้องออกแบบเรื่อง "แก้ในนามใคร" ก่อน
- **Scope ระดับหมวด** สำหรับเปิดให้ผู้ตรวจสอบภายนอกเห็นเฉพาะบางหมวด

## 7. Decisions & Open Questions

### ตัดสินใจแล้ว (2026-08-27)

| # | ประเด็น | มติ | ผลที่ตามมา |
|---|---|---|---|
| **D1** | `owner` เป็นชื่อคนจริง ถือเป็นข้อมูลส่วนบุคคลที่ต้องปิดบังไหม | **ไม่ต้องปิดบัง** ส่งออกได้ตามจริง | R4 คืน `owner` ตรง ๆ ไม่ต้องทำ scope แยกหรือ masking — ตัดความซับซ้อนออกได้ทั้งก้อน |
| **D2** | token ควรบังคับหมดอายุไหม | **ไม่หมดอายุ** ใช้การเพิกถอนเป็นกลไกควบคุมแทน | คอลัมน์ `expires_at` ยังอยู่ (กรอกเองได้) แต่ค่าเริ่มต้นเป็น null · **แลกมาด้วยภาระเฝ้าระวัง** — R1 จึงเพิ่มข้อบังคับให้หน้า Admin โชว์ `last_used_at` และเน้นใบที่เงียบเกิน 90 วัน และ IP allowlist มีน้ำหนักขึ้นเป็นด่านที่สอง |
| **D3** | ความเห็นใน workflow history ให้ AI ภายนอกอ่านได้เลยไหม | **แยก scope** (`history:read`) | R6 แยกสิทธิ์ออกจาก `items:read` · scope เริ่มต้นของ token ใหม่ **ไม่มี** `history:read` ต้องติ๊กเอง · token ที่ออกให้ Morning Brief ไม่ควรมี scope นี้ |

**สิ่งที่ D2 เปลี่ยนไปจากร่างแรก:** เดิมคิดว่าอายุ token จะเป็นตัวจำกัดความเสียหายเมื่อ token หลุด พอไม่มีวันหมดอายุ ความเสียหายจะยืดไปเรื่อย ๆ จนกว่าจะมีคนสังเกตเห็น เลยย้ายน้ำหนักไปที่ **"ต้องเห็นได้ง่ายว่าใบไหนยังมีชีวิตอยู่"** แทน ซึ่งเป็นเหตุผลที่ R1 เพิ่มข้อ `last_used_at` และผมเสนอให้ชั่งดัน IP allowlist ขึ้น P0
