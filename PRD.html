ITGR Dashboard เป็นระบบติดตามการปฏิบัติตาม Marubeni Group IT Governance Rules (ITGR) Checklist (96 ข้อกำหนด, 8 หมวด) ของ AutoCorp — เดิมเป็นไฟล์ HTML เดี่ยวที่เก็บสถานะไว้ใน localStorage ของเบราว์เซอร์ (ข้อมูลไม่แชร์กัน ไม่มี audit trail ไม่มีการควบคุมสิทธิ์) — ปัจจุบันย้ายเป็นระบบหลายผู้ใช้เต็มรูปแบบบน Supabase + Vercel serverless BFF พร้อม PIN login, RBAC, workflow อนุมัติแบบแบ่งแยกหน้าที่ (User → Reviewer → Approver), และ API สำหรับระบบภายนอก

เอกสารนี้ครอบคลุมทุกฟีเจอร์ตั้งแต่ v1.0 (migration พื้นฐาน) ถึง v1.8 (self-assessment บน External API) — verified ล่าสุด 2026-09-08 ว่าข้อมูลใน repo, ฐานข้อมูล production, และไฟล์ต้นฉบับ workbook FY2026 ตรงกันทั้งหมด (re-run การแตกไฟล์แล้วได้ผลลัพธ์เหมือนเดิมทุกตัวอักษร)

🎯 เป้าหมาย & Non-Goals

เป้าหมายหลัก

  • ข้อมูลทุกอย่างอยู่ใน Supabase เป็น single source of truth — ไม่มีอะไรอยู่แค่ใน localStorage หรือ client bundle
  • Frontend ไม่คุยกับ Supabase ตรง — ผ่าน BFF เท่านั้น service key ไม่หลุดถึงเบราว์เซอร์
  • สิทธิ์ควบคุมด้วย PIN login + 3 ระดับ role ตรวจสอบฝั่งเซิร์ฟเวอร์เสมอ ไม่ใช่แค่ซ่อน UI
  • ทุกการแก้ไข status/owner/note ระบุตัวคนและเวลา (audit log)
  • (v1.3) ไม่มีข้อไหนถูกตัดสิน Compliant/NC โดยไม่ผ่าน Reviewer และ Approver แยกจากคนเตรียมหลักฐาน
  • (v1.3) งาน ClickUp เชื่อมกับข้อกำหนดโดยตรง ไม่ต้องทำ mapping สองที่

สิ่งที่ตั้งใจไม่ทำ (Non-Goals)

  • Self-service signup / SSO / email login — เครื่องมือภายในทีมเล็ก ใช้ PIN พอ
  • Real-time collaboration (live cursor, conflict UI) — last-write-wins เพียงพอสำหรับ checklist ขนาดนี้
  • แก้เนื้อหา checklist master ผ่าน UI — แก้ตรงใน Supabase ได้ถ้าจำเป็น
  • แอปมือถือแยก — เป็น responsive web app
  • (v1.3) ผูก ClickUp API ลึก (แค่ URL field ไม่ sync สถานะ)
  • (v1.3) Multi-reviewer/approver พร้อมกันต่อข้อ — เป็นแบบคนเดียวต่อขั้น
  • (v1.6) เขียน/แก้ข้อมูลผ่าน API ภายนอก, เดิน workflow ผ่าน API, ดึงไฟล์หลักฐานผ่าน API

1. การยืนยันตัวตน

v1.0 · shipped
  • เข้าสู่ระบบด้วย PIN เท่านั้น (ไม่มี username/email) — เหมาะกับทีมเล็กที่รู้จักกันชัดเจน
  • PIN ถูก hash ด้วย HMAC-SHA256 + pepper ก่อนเก็บ — ไม่เก็บ/log เป็น plaintext เด็ดขาด
  • ล็อกอินสำเร็จได้ session cookie แบบ httpOnly + secure + sameSite: strict (JWT อายุ 8–12 ชม.)
  • ทุก endpoint (ยกเว้น login) ต้องมี session ที่ถูกต้อง endpoint ที่แก้ไขข้อมูลต้องมี role ที่เหมาะสมด้วย — ตรวจฝั่งเซิร์ฟเวอร์เสมอ
  • ข้อความ error ทั่วไปเดียวกันหมด ไม่บอกว่า "PIN ไม่มีอยู่" หรือ "PIN ผิด" เพื่อไม่ให้เดา PIN ที่มีอยู่จริงได้

2. Checklist Tracker

v1.0 · shipped

ติดตาม 96 ข้อกำหนดใน 8 หมวด — แต่ละข้อมี status (Not Started / In Progress / Compliant / Partial / Not Compliant / Not Applicable), owner (ผู้รับผิดชอบ), note (หลักฐาน/หมายเหตุ), และ ClickUp task link

  • แท็บ Overview / Tracker / By Category / Reference / Appendix — ครบเหมือนระบบเดิม ดึงข้อมูลจาก BFF แทนค่าคงที่ในโค้ด
  • ผู้ใช้ read_only เห็น input เป็น plain text ไม่มีช่องแก้ไข
  • ทุกการแก้ status/owner/note เขียนลง audit_log — ใคร แก้ฟิลด์ไหน จากอะไรเป็นอะไร เมื่อไหร่

3. Radar Chart & เกรดรวม

v1.1–v1.2 · shipped
  • Compliance Radar Chart — กราฟเรดาร์ 8 แกน (1 แกน/หมวด) แสดง % ความคืบหน้าพร้อมเกรด A–E ต่อหมวด บนแท็บ Overview เพิ่มเติมจากแถบ progress เดิม
  • เกณฑ์เกรด: A ≥80% · B ≥60% · C ≥40% · D ≥20% · E <20% (รวมขอบล่างเข้าเกรดบน ไม่มีช่องว่างหรือทับซ้อน)
  • Overall Grade — เกรดเดียวรวมทั้ง 96 ข้อ 8 หมวด คำนวณจากเกณฑ์เดียวกัน
  • Priority Status Panels — สรุปแยกเฉพาะข้อ Top Priority (◎) และ Priority (〇) ไม่รวมข้อที่ไม่มีลำดับความสำคัญ
  • คำนวณฝั่ง client ทั้งหมดจากข้อมูลที่ GET /api/items คืนมาอยู่แล้ว — ไม่ต้องแก้ schema หรือ BFF

4. Approval Workflow

v1.3 · shipped

แต่ละข้อมี workflow_state แยกจาก status ที่แสดงผล — เดินตามลำดับที่บังคับแบ่งแยกหน้าที่:

Not Started→ In Progress→ Pending Review→ Pending Approval→ Compliant / Complied w/ Condition / Not Compliant
  • Submit for Approval (User) — ต้องกรอก Owner + Evidence ก่อนส่งได้ (ClickUp ไม่บังคับ)
  • Reviewer — OK (ไปต่อ Approver, comment ไม่บังคับ) หรือ Reject (กลับ User, comment บังคับ)
  • Approver — Compliant / Complied with Condition (ต้องมีไฟล์แนบหรือ comment อย่างน้อย 1 อย่าง) / Not Compliant / หรือ Reject กลับ User
  • ทุก transition เขียนลง item_workflow_events — actor, from-state, to-state, comment, ไฟล์แนบ, เวลา — เป็นทั้ง audit trail และประวัติ comment ที่ User เห็นตอนถูกตีกลับ
  • ไฟล์หลักฐานเก็บใน Supabase Storage (private bucket) แจกผ่าน signed URL อายุสั้นเท่านั้น ไม่มี public URL

8. External Read API

v1.6–v1.7b · shipped

ให้ระบบภายนอก (n8n, LINE bot, Claude ฯลฯ) อ่านสถานะ ITGR ได้โดยตรงผ่าน /api/v1/* — อ่านอย่างเดียวเสมอ ใช้ token แยกขาดจากระบบ PIN login โดยสิ้นเชิง

EndpointScopeใช้ทำอะไร
/metatoken ใด ๆคำอธิบายทุก enum/filter + ตัวอย่างคำถาม — หัวใจของการถามแบบ Vibe
/itemsitems:readค้น/กรอง 96 ข้อ (รวม self_assessment ตั้งแต่ v1.7b)
/items/{no}items:readรายละเอียดข้อเดียว
/items/{no}/historyitems:read + history:readไทม์ไลน์ workflow (scope แยก — มีชื่อคนและปัญหาที่ยังไม่เสร็จ)
/summarysummary:readตัวเลขสรุป — คำนวณด้วยตรรกะเดียวกับ Overview เป๊ะ
  • Token ไม่หมดอายุเองโดยดีฟอลต์ (ตัดสินใจแล้ว) — ใช้การเพิกถอนเป็นกลไกควบคุมแทน หน้า Admin จึงต้องโชว์ "ใช้ล่าสุด" ให้เห็นชัด
  • Rate limit 60 request/นาที/token, ทุก request บันทึกลง api_request_log — เขียน log ก่อนส่ง response เสมอ (ดูกล่องด้านล่าง — บทเรียนจริงจากการ deploy ครั้งแรก)
  • ไม่ส่ง CORS header ใด ๆ — token ใช้จาก JavaScript ในเบราว์เซอร์คนอื่นไม่ได้
⚠️ บทเรียนจาก production จริง: deploy รอบแรก (27 ส.ค.) เขียน log หลัง ส่ง response — Vercel serverless ไม่การันตีว่างานที่ทำหลังส่ง response แล้วจะรันจบ ผลคือบันทึกได้แค่ 1 ใน 9 request จริง แก้โดยสลับเป็น เขียน log ก่อน แล้วค่อยส่ง response เสมอ ยืนยันแล้วว่าบันทึกครบ 100% หลังแก้

รายละเอียด endpoint ครบทุกพารามิเตอร์ + ตัวอย่างจริง + วิธีต่อกับ n8n/Claude/LINE ดูที่ api-docs.html →

① ฉบับ 8 ก.ย. เข้าใจผิดว่าเป็น comment ของ Box บนโฟลเดอร์ต่อข้อ — จริง ๆ คือ เนื้อหาในเซลล์ คอลัมน์ "Remarks Column" ของไฟล์เดียว
② ฉบับ 9 ก.ย. เช้า แก้ถูกแล้วแต่ยังออกแบบให้เขียนกลับได้ (ฉบับนี้รัน migration ขึ้น production ไปแล้ว — คอลัมน์ที่ไม่ใช้แล้วมีสคริปต์ลบให้เลือกรันท้าย schema.sql)
③ ฉบับสุดท้าย: ทางเดียว อ่านอย่างเดียว เพราะไฟล์เป็นของ Marubeni เราได้แค่ลิงก์อ่าน

ไฟล์ checklist ของ Marubeni มีคอลัมน์ "Remarks Column" (คอลัมน์ T) ที่เขียนเหตุผลของผลตรวจไว้รายข้อ — เดิมอ่านเข้าระบบครั้งเดียวตอน seed แล้วก็นิ่ง ทั้งที่ Marubeni ยังแก้ไฟล์ตัวจริงของเขาเรื่อย ๆ · v1.9 ทำให้ อัปโหลดไฟล์ล่าสุดเข้ามา แล้ว Remark ทุกข้ออัปเดตตาม โดยไม่ต้องพิมพ์ซ้ำ

✅ ตัดสินใจแล้ว

  • D1-D2 · ไฟล์เดียวทั้งระบบ · "comment" = ค่าในเซลล์ ไม่ใช่ comment thread ของ Box (Box ไม่มี comment รายแถวอยู่แล้ว)
  • D3 · Remark ไม่แตะ status จริง — เหมือนหลักการ self-assessment (v1.7): มีแค่ User → Reviewer → Approver ที่ตั้งผลตัดสินได้ ไฟล์ที่ใครก็แก้ได้ต้องไม่กลายเป็นทางลัดข้าม workflow
  • D4 · เพิ่ม role marubeni — คนฝั่ง Marubeni: ดูได้ + กดนำเข้า Remark ได้ แค่นั้น
  • D5 · ทางเดียว ไม่เขียนกลับ — ไฟล์เป็นของ Marubeni เราได้ลิงก์อ่านอย่างเดียว ถ้าจะเขียนต้องให้เขาเชิญเป็น Editor และยังมีคำถามว่า ผู้ถูกตรวจควรไปเขียนไฟล์ควบคุมของผู้ตรวจไหม
  • D6 · อัปโหลดเอง ไม่ต่อ API — พอไม่เขียนกลับ การดึงอัตโนมัติเหลือประโยชน์แค่ "ไม่ต้องมีคนกด" แต่ต้องแลกกับ OAuth + เก็บ token + ต่ออายุ ไม่คุ้มกับไฟล์ที่นาน ๆ เปลี่ยนที
🧪 ทดสอบกับไฟล์จริงแล้ว (lib/checklistRemarks.js + exceljs): หาคอลัมน์จากข้อความหัวตาราง ไม่ฮาร์ดโค้ดตัวอักษร · จับคู่แถวด้วยเลขข้อ ไม่ใช่ตำแหน่งแถว · อ่านครบ 96/96 ข้อ (พบ 58 ข้อที่มีข้อความ) · เซลล์แบบ rich text แปลงถูกต้อง (ถ้าอ่านตรง ๆ จะได้ [object Object] แบบเงียบ ๆ) · เขียนเฉพาะแถวที่เปลี่ยนจริง เพื่อให้ "อัปเดตล่าสุด" มีความหมาย · ไฟล์ที่ไม่ใช่ workbook ขึ้น error ชัดเจนและถูกบันทึกลง log
  • การ์ด นำเข้า Remark อยู่บนแท็บ Tracker (ไม่ใช่ Admin เพราะ marubeni เข้า Admin ไม่ได้) — เห็นเฉพาะ marubeni/admin · มีลิงก์ไปเปิดไฟล์ใน Box เพื่อโหลดตัวล่าสุด
  • Panel "Remark จากไฟล์ checklist" ในแต่ละข้อ — อ่านอย่างเดียวสำหรับทุกคน ไม่มีใครแก้ในแอปได้ จึงไม่มีข้อมูล 2 เวอร์ชันให้ขัดกัน
  • ทุกครั้งที่นำเข้าบันทึกลง remark_import_log (1 แถวต่อ 1 ครั้ง) ทั้งสำเร็จและล้มเหลว
  • ถ้ายังไม่ได้รัน migration ระบบไม่พัง — อ่านจะ fallback ลงชั้นก่อนหน้า และการนำเข้าจะขึ้น 501 พร้อมบอกว่าต้องรัน migration
💡 สิ่งที่ได้จากการ "ตัดขาเขียนกลับ" ออก: blocker หายหมดในทีเดียว — ไม่ต้องมี Box Custom App, ไม่ต้องให้ Box admin อนุมัติ, ไม่ต้องขอ Marubeni เชิญเป็น Editor, ไม่ต้องเก็บ credential ที่ต้องต่ออายุ, ไม่มีความเสี่ยงเขียนทับงานคนอื่นตอนแก้ไฟล์พร้อมกัน และไม่ต้องตอบคำถามว่าผู้ถูกตรวจควรเขียนไฟล์ผู้ตรวจไหม

📈 Success Metrics

Leading (2–4 สัปดาห์แรก)

  • ทีม COE&S/ATC ทุกคนมี PIN login ใช้งานได้ 100%
  • ไม่มีรายงาน "ข้อมูลหาย" จาก localStorage อีก
  • ทุกการแก้ไข tracker มี updated_by ถูกต้อง
  • (v1.3) 100% ของข้อที่ submit ใหม่ผ่าน Reviewer + Approver ก่อนถึงสถานะจบ
  • (v1.6) เวลาจากออก token ถึงยิงคำถามแรกสำเร็จ ≤ 10 นาที

Lagging (จบรอบตรวจ)

  • Dashboard เป็น system of record ในการตรวจจริงของ Marubeni พร้อม audit trail ครบ
  • ไม่มี read-only stakeholder คนไหนต้องขอสิทธิ์แก้ไขเป็นทางลัด
  • (v1.3) เวลาเฉลี่ยจาก Submit ถึงตัดสินสุดท้าย — ใช้ตั้ง baseline
  • (v1.6) จำนวนครั้งที่ต้องเปิดเว็บแค่เพื่อเช็คสถานะ ลดลง ≥ 50% เมื่อมี automation ใช้ API จริง

❓ คำถามที่ยังค้างอยู่

คำถามที่ตอบแล้วถูกตัดออกจากรายการนี้ (ดูประวัติเต็มใน PRD.md) — เหลือเฉพาะที่ยังไม่ปิด:

  • Retention ของ audit log — ยังไม่มีนโยบายลบ/เก็บ สันนิษฐานว่าเก็บไม่จำกัดช่วงรอบ FY2025
  • Rate limiting การล็อกอิน PIN — ยังไม่บังคับ lockout หลังพยายามผิดหลายครั้ง (P1)
  • Reviewer/Approver ควรแบ่งตามหมวดไหม — ตอนนี้เป็น global ทุกคน 96 ข้อ อาจเป็นคอขวดถ้าทีมเล็ก
  • (v1.6) 60 request/นาทีพอไหมสำหรับ automation แบบ batch — รอดูการใช้จริงเดือนแรก
  • (v1.6) เก็บ api_request_log นานแค่ไหน — เสนอ 90 วัน ยังไม่ยืนยัน
  • (v1.6) ควรทำ openapi.json + IP allowlist ต่อ token ไหม — ยังไม่ได้ตัดสินใจ (ดู § 8 P1 roadmap)
  • (v1.9 — blocking ก่อนออกบัญชีจริง) role marubeni คือการเปิดให้คนนอก AutoCorp login เข้าระบบได้จริงเป็นครั้งแรก — ต้องขอ go-ahead จากเจ้าของนโยบายข้อมูลก่อน ไม่ใช่แค่ตัดสินใจเชิงเทคนิค
  • (v1.9) marubeni ควรเห็นประวัติ workflow/comment ภายใน (Reviewer/Approver) ด้วยไหม — ค่าเริ่มต้นที่เสนอคือ "ไม่เห็น"
  • (v1.9) self_assessment_note (แช่ไว้ตอน seed) กับ box_remark (อัปเดตทุกครั้งที่ import) มาจากคอลัมน์เดียวกัน — ตั้งใจให้แยกกัน แต่ต้องยืนยันว่าคนตรวจอ่านแล้วไม่สับสน
  • (v1.9) Marubeni อัปเดตไฟล์บ่อยแค่ไหน — ถ้ากลายเป็นทุกสัปดาห์ ค่อยกลับมาคิดเรื่องดึงอัตโนมัติ

💡 ข้อเสนอแนะ

เรียงตามผลกระทบ/ความพยายามที่คาดว่าจะได้ — รายละเอียดเต็มใน PRD.md § 11

  1. ตัวนับ "รอคุณอยู่" ในแอปสำหรับ Reviewer/Approver — ไม่มีสิ่งนี้ workflow จะรอคนจำได้เองว่าต้องเข้ามาเช็ค เป็นความเสี่ยงอันดับ 1 ที่ทำให้ workflow ค้าง
  2. Reviewer/Approver แยกตามหมวด — คุ้มค่าพิจารณาเมื่อรู้จำนวนคนจริงที่จะทำสองบทบาทนี้
  3. SLA/อายุของ Pending Review/Approval — แค่คอลัมน์ "ค้างกี่วัน" ก็ทำให้เห็นข้อที่ค้างได้โดยไม่ต้องสร้างระบบแจ้งเตือน
  4. Comment thread เต็ม ไม่ใช่แค่เหตุผลตีกลับล่าสุด — สำคัญเมื่อข้อหนึ่งถูกตีกลับมากกว่า 1 รอบ
  5. เก็บไฟล์หลักฐานแบบ versioning ไม่ทับของเดิม — สำคัญต่อการยืนยันย้อนหลังว่า ณ เวลาตัดสิน มีหลักฐานอะไรอยู่จริง
  6. Export ชุดการตัดสินใจ (PDF) ต่อข้อ/หมวด — การส่ง Marubeni จริงน่าจะต้องการสรุปสะอาด ไม่ใช่ลิงก์ dashboard สด
